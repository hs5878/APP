# DECISIONS — 연애기록 앱

- 형식: `D-번호 · 제목 · 상태` / 결정 / 이유 / 대안(버린 것)
- 상태: **확정**(요청자가 정함) · **기본값**(제안으로 진행 중, 바꿀 수 있음) · **결정 필요**
- 최종 갱신: 2026-10-03 (v0.3, REVIEW.md 수정안 반영. 기존 항목은 `보완:` 줄로 이어 적었다)
- 새 결정은 아래에 번호를 이어 붙인다. 뒤집을 때는 지우지 말고 상태를 `대체됨 → D-xxx`로 바꾼다.

---

### D-001 · 기술 스택 · 확정
- 결정: Expo(React Native) + TypeScript, iOS/Android 배포. 기획·설계는 이 프로젝트에서, 구현은 Claude Code에서 한다.

### D-002 · MVP 기능 범위 · 확정
- 결정: F1 커플 연결·기념일, F2 사진 자동 정리, F3 AI 초안, F4 내보내기·Drive 백업, F5 PDF 포토북, F6 기본 보안. 세부는 SPEC §2.
- 이유: 요청자가 제시한 6개 기능을 그대로 MVP로 확정하고, 각 기능 안에서 범위를 줄였다.

### D-003 · 기기 우선 + 얇은 동기화 서버 · 기본값
- 결정: 로컬 SQLite가 원본이다. 서버(Supabase)는 커플 공간 동기화 중계, 인증, 초대 코드, AI·장소 프록시만 맡는다.
- 이유: "기기 내 저장 우선"과 "초대 코드로 공유 공간"은 서버 없이는 함께 만족할 수 없다. 서버 역할을 중계로 한정하면 둘 다 지킬 수 있다.
- 대안: 서버 없는 1인 앱(커플 연결이 빠져서 탈락). 서버 원본 구조(기기 우선 원칙과 충돌해서 탈락).

### D-004 · 백엔드는 Supabase · 기본값
- 결정: Auth, Postgres + RLS, Storage, Edge Functions, Realtime을 Supabase 하나로 쓴다.
- 이유: 혼자 개발할 때 운영 부담이 가장 적다. RLS로 "공간 멤버만 접근"을 DB에서 강제할 수 있고, Postgres라서 이전도 쉽다.
- 대안: Firebase(문서형 DB라 동기화 rev 설계가 불편함), 자체 서버(MVP 단계에서는 과함).
- 참고: Storage 무료 한도는 작으므로 사진 보관본(약 0.5MB/장) 기준으로 출시 전에 유료 플랜 전환 시점을 계산한다.

### D-005 · 공유 데이터는 종단간(E2E) 암호화 · 확정 (2026-10-03)
- 결정: 서버에 올라가는 사진(보관본, 썸네일)과 기록 내용은 기기에서 암호화한 뒤 올린다. 서버는 복호화 키를 갖지 않는다. 원본과 후보 사진은 지금처럼 기기에만 둔다.
- 이유: 요청자가 표준 암호화 대신 선택했다. 커플 사진 유출은 치명적이고, "기기 우선" 신뢰 메시지와 일관된다.
- 버린 대안: 서버 측 표준 암호화(서버 운영자가 볼 수 있음), 사진 미공유(상대 사진을 못 봄).
- 세부: 키 교환 D-019, 암호화 범위 D-020, 키 분실과 복구 D-021.

### D-006 · 로그인 수단 · 기본값
- 결정: 카카오, Apple 로그인. 로그인은 온보딩에서 필수다.
- 이유: 국내 사용자는 카카오가 기본이고, 소셜 로그인을 쓰는 iOS 앱은 Apple 로그인이 필요하다. 처음부터 계정이 있어야 연결과 합치기가 단순해진다.
- 대안: 로그인 없이 시작(로컬 → 계정 이전 흐름이 하나 더 생겨서 제외).
- 보완(v0.3): Android에서도 웹 OAuth로 Apple 로그인을 제공한다. 아이폰에서 Apple로 가입한 사람이 안드로이드로 바꾸면 같은 계정으로 들어와야 새 기기 승인이 된다. Supabase 카카오 공급자가 이메일 동의 항목을 요구해 비즈 앱 전환이 필요한지는 M4 첫 작업에서 확인한다.

### D-007 · 데이트 묶음 규칙 · 기본값
- 결정: 하루 경계 04:00, 사진 간격 3시간 이하면 같은 묶음, 3장 미만은 후보 제외, 묶음 안에서 150m 이내 연속 사진은 같은 장소 스톱.
- 이유: 갤러리 사진은 대부분 데이트가 아니므로 완전 자동 확정은 위험하다. 대신 "후보 → 한 번 탭 확정"으로 사용자 일을 카드당 한 번으로 줄인다.
- 대안: 전부 자동 확정(업무·음식 사진이 섞임), 위치 이동으로 분할(하루 데이트가 여러 카드로 쪼개짐).
- 수치는 상수로 두고 실제 사진으로 테스트하면서 조정한다.

### D-008 · 사진 보관 방식 · 기본값
- 결정: 갤러리 원본은 참조(asset id)만 하고, 앱 안에는 보관본(긴 변 2048px, JPEG 85%)을 복사해 둔다. 내보내기 때는 원본이 갤러리에 남아 있으면 원본, 없으면 보관본을 쓴다.
- 이유: 원본을 전부 복사하면 저장 공간이 두 배가 된다. 참조만 하면 갤러리에서 지웠을 때 기록이 깨진다.
- 대안: 원본 전체 복사, 참조만 저장.
- 보완(v0.3): 원본은 원래 형식(JPG 또는 HEIC) 그대로 내보낸다. iCloud에서 받지 못하면 보관본 JPG를 쓴다. 상대 사진은 보관본만 있다.

### D-009 · AI 초안 입력과 모델 · 기본값
- 결정: Edge Function이 Claude API를 호출한다. 입력은 날짜, 요일, 장소명·카테고리·동, 사진 수다. 이미지, 좌표, 이름은 보내지 않는다. 비용이 낮은 소형 모델을 쓰고, 모델 ID는 환경 변수로 둔다. 공간당 하루 30회로 제한한다.
- 이유: 사진을 보내지 않는다는 보안 약속을 지킨다. "파스타" 같은 구체성은 장소 카테고리(예: 음식점 > 양식 > 이탈리안)에서 나온다.
- 한계: 장소 정보가 없는 카드는 문장이 밋밋해진다. 온디바이스 이미지 라벨링은 v1.1에서 검토한다.

### D-010 · 장소 조회는 카카오 로컬 API · 기본값
- 결정: Edge Function을 거쳐 카카오 로컬 API(좌표 → 행정동, 주변 카페·음식점·관광명소·문화시설)를 호출한다. 앱에는 키를 넣지 않는다. 서버는 좌표를 저장하지 않는다.
- 이유: 국내 상호명과 카테고리 품질이 가장 좋다.
- 영향: 좌표가 카카오로 전달되므로 데이터 약속 화면에 고지한다. 설정에서 끌 수 있다.

### D-011 · 로컬 저장 암호화 · 기본값
- 결정: DB는 SQLCipher(expo-sqlite 옵션)로 암호화하고, 무작위 256비트 키를 SecureStore에 둔다. 사진 파일은 앱 샌드박스와 OS 파일 암호화에 맡긴다. 앱 수준 사진 암호화는 v1.1.
- 이유: 기록 텍스트와 위치를 확실히 보호하면서, 사진을 볼 때마다 복호화하는 성능 비용을 피한다.
- PIN과 DB 키는 분리한다. 그래서 PIN을 잊어도 재로그인으로 데이터를 잃지 않는다.

### D-012 · 백업은 Google Drive, 일반 형식 · 기본값
- 결정: `drive.file` 범위로 내 드라이브에 보이는 폴더에 JPG와 JSON 형태로 백업한다. 하루 한 번, Wi-Fi에서, 증분으로 한다. 복원 기능도 MVP에 넣는다.
- 이유: "앱 없이도 열리는 내 데이터"가 신뢰 포인트다. 복원이 없으면 백업은 의미가 없다.
- 대안: 숨김 앱 폴더(appDataFolder)나 암호화 백업(사용자가 직접 열 수 없어서 신뢰 메시지가 약해짐).
- 보완(v0.3): Drive에는 보관본만 올린다(원본 포함은 내보내기에서만). 파일 경로는 `photos/YYYY-MM-DD/{photo_id}.{ext}`로 처음 정한 뒤 바꾸지 않는다. iOS 백그라운드 실행 시간이 짧아서 "하루 한 번"은 "앱 실행 때 24시간이 지났으면 시작, 백그라운드는 data.json만"으로 기대치를 낮춘다.

### D-013 · 포토북은 PDF까지 · 기본값
- 결정: 기기에서 expo-print로 200×200mm PDF를 만든다. 인쇄는 PDF 저장·공유와 외부 업체 안내 링크만 제공한다. 업체 제휴와 인쇄용 규격(재단 여백, CMYK)은 v1.1.
- 이유: 요청자 제안대로 실물 제작은 MVP에서 하지 않는다. 업체마다 업로드 규격이 달라서, 제휴 업체가 정해지면 그때 맞춘다.
- 생성 시점: OS가 백그라운드 실행을 보장하지 않으므로 알림 이후 처음 앱을 열 때 만든다.

### D-014 · 위치정보법 확인 · 결정 필요(출시 전)
- 사진 위치를 서버 경유로 조회하므로 위치기반서비스사업 신고 대상인지 출시 전에 법률 확인이 필요하다. 개발은 막지 않는다.

### D-015 · 서비스 종료 약속 · 기본값
- 결정: 종료 최소 3개월 전 앱 안 공지, 종료 후에도 내보내기가 동작하는 기간 제공. 약관과 설정 > 데이터 약속에 명시한다.
- 이유: 요청자가 말한 "최소 몇 개월"을 업계에서 흔히 쓰는 3개월로 정했다. 약관 문구는 법률 검토를 거친다.

### D-016 · 연결 해제 처리 · 기본값
- 결정: 한쪽이 해제할 수 있다. 각자 기기 데이터는 남고, 서버 데이터는 30일 유예 뒤 삭제한다. 유예 기간에 두 사람이 모두 동의하면 복구한다.
- 이유: 국내 커플 앱의 일반적인 기대치(실수로 해제한 경우 복구)와 개인정보 최소 보관 사이의 절충이다.
- 보완: 해제 이후 화면과 복구 절차는 D-025.

### D-017 · 날짜 규칙 · 기본값
- 결정: 사귄 날이 1일이다. 자동 기념일은 100일 단위와 매 주년이다. 2월 29일 시작이면 평년에는 2월 28일로 계산한다. 날짜 계산은 `YYYY-MM-DD` 문자열로만 하고 시간대 변환을 하지 않는다.
- 이유: 한국 커플 앱의 관례다. 시간대 변환을 하지 않으면 해외여행 중에도 날짜가 밀리지 않는다.

### D-018 · MVP에서 뺀 것 · 기본값
- 결정: 상대 활동 푸시(승인 요청 푸시는 예외, D-027), 복구 코드와 키 재발급(D-021, D-023), 한 기기 여러 계정·여러 공간, 음력 기념일, 위젯, 대체 앱 아이콘, 동영상, 여러 날 여행 묶음, 다국어. 전체 목록은 SPEC §2.
- 이유: 6개 핵심 기능을 출시 가능한 품질로 만드는 데 집중한다. 알림 숨김의 다음 단계인 대체 아이콘이 v1.1 1순위다.

### D-019 · 키 교환: 연결 승인과 확인 숫자 · 기본값
- 결정: 공간을 만들 때 공간 키(무작위 256비트)를 기기에서 만든다. 기기마다 X25519 키쌍을 만들어 공개키만 서버에 등록한다.
- 연결 흐름: 상대가 초대 코드를 입력 → 서버에 연결 요청과 상대 기기 공개키가 올라감 → 초대한 사람 화면에 "연결 요청"과 6자리 확인 숫자가 뜸(두 공개키와 코드로 계산, 두 화면에 같은 숫자) → 같은지 확인하고 승인 → 내 기기가 공간 키를 상대 공개키로 봉인해 서버에 올림 → 상대 기기가 풀어서 보관.
- 새 기기(폰 교체)도 같은 흐름이다. 상대 기기나 내 예전 기기가 승인한다.
- 이유: 초대 코드 8자리로는 키를 안전하게 나를 수 없고, 키를 링크에 넣으면 메신저 서버를 거친다. 확인 숫자는 서버가 중간에서 키를 바꿔치기하는 것을 막는다.
- 대가: 연결할 때 초대한 사람이 앱에서 승인해야 한다. 요청은 24시간 유지된다.
- 구현: react-native-libsodium(X25519 봉인 상자, XChaCha20-Poly1305). 직접 만든 암호 코드는 쓰지 않는다.
- 보완(v0.3): 확인 숫자 계산은 D-022(커밋-공개)로 바꿨다. 위의 "두 공개키와 코드로 계산"은 서버가 맞출 수 있어서 쓰지 않는다. 승인 기기에는 푸시가 간다(D-027).

### D-020 · 암호화 범위 · 기본값
- 결정: 사진 파일(보관본, 400px 썸네일)과 동기화 행의 내용 필드(사귄 날, 별명, 요약, 메모, 장소명, 기념일 제목·날짜 등)를 암호화한다.
- 서버 평문(v0.3 수정): ID, 소속 관계(space, card), 작성자 ID, key_id, rev, 생성·수정·삭제 시각, 공간 상태(status, unlinked_at), 멤버 역할과 합류 시각, 기기 공개키와 기기명, 푸시 토큰, 초대·승인 요청의 상태와 만료 시각, 사진 저장 경로(ID만 포함).
- 암호화 방식(v0.3 수정): 행은 XChaCha20-Poly1305 AEAD로, AAD에 테이블명·id·space_id·parent_id·작성자·key_id를 묶는다. 사진 파일도 단발 AEAD로 암호화하고 AAD에 photo_id·space_id·key_id·보관본/썸네일 구분을 묶는다. secretstream은 react-native-libsodium 네이티브 구현에 없어서 쓰지 않는다.
- 이유: 사진만 암호화하고 기록 문장이 평문이면 약속이 반쪽이 된다. 동기화는 ID와 rev만으로 돌아가므로 서버가 내용을 알 필요가 없다.
- 예외(고지 필수): AI 초안(장소명, 날짜)과 장소 조회(좌표)는 처리하는 순간 서버 함수를 평문으로 지나간다. 저장하지 않으며, 설정에서 둘 다 끌 수 있다.
- 서버가 알 수 있는 것: 카드·사진 개수, 활동 시각, 대략적인 파일 크기.
- 한계(고지): 서버는 행을 지우거나 예전 암호문으로 되돌릴 수 있다. MVP에서는 막지 않는다.

### D-021 · 키 분실과 복구 · 기본값 (둘 다 분실 시 처리는 D-023으로 보완)
- 결정: 한 사람이 기기를 잃으면 상대 기기가 새 기기를 승인해서 복구한다. 두 사람이 모두 기기를 잃으면 서버 데이터는 복호화할 수 없다. 이때는 Google Drive 백업(일반 형식)으로 복원한 뒤 새 공간 키로 다시 올린다.
- 1인 공간에서 기기를 잃으면 Drive 백업만이 복구 수단이다.
- 이유: 복구 코드(24단어)는 대부분 사용자가 보관하지 않아서 MVP에서는 실효성이 낮다. Drive 백업이 사실상 복구 수단 역할을 한다.
- UX: 연결 직후와 설정 화면에서 "Drive 백업을 켜야 두 기기를 모두 잃어도 복구돼요"를 안내한다. 복구 코드는 v1.1에서 검토한다.
- 보완(v0.3): "새 공간 키로 다시 올린다"는 키 재발급 없이 새 공간을 만드는 방식으로 한다(D-023). 새 기기 승인이 끝나면 예전 기기는 revoke되고 세션이 모두 끊긴다.

### D-022 · 확인 숫자는 커밋-공개 순서로 계산 · 기본값 (D-019 보완)
- 결정: 요청 기기가 무작위 n_R의 커밋 `BLAKE2b(pk_R ‖ n_R)`을 먼저 올리고, 승인 기기가 무작위 n_A를 올린 뒤에야 n_R을 공개한다. 승인 기기는 커밋을 확인한 뒤에만 숫자를 보여준다. 숫자 = `BLAKE2b(pk_A ‖ pk_R ‖ n_A ‖ n_R ‖ request_id)` 앞 8바이트 mod 10⁶.
- 이유: 기존 공식은 입력이 모두 서버가 아는 값이라, 중간자 서버가 가짜 키를 100만 번쯤 바꿔 만들어 두 화면 숫자를 맞출 수 있었다. 커밋-공개면 서버가 미리 맞출 확률이 100만분의 1이다.
- 대가: 두 기기가 같은 시점에 온라인이어야 한다. 나란히 놓고 비교하는 상황이라 문제가 작다. 세부 흐름은 DATA_MODEL §5.2.

### D-023 · 두 사람 모두 기기를 잃으면 새 공간으로 복원 · 기본값 (D-021 보완)
- 결정: 옛 공간은 서버에서 삭제하고, Drive 백업을 새 공간(새 space_id, 새 공간 키)으로 복원한 뒤 상대를 다시 초대한다. 키 재발급(key_id 증가)은 계속 v1.1이다.
- 흐름: 새 기기 로그인 → 승인할 활성 기기가 없음 → [Drive에서 복원] 또는 [새로 시작] → 복원 시 data.json의 space_id를 새 값으로 바꿔 넣고 전체 push → 옛 공간 `reset-space` 호출(서버 행·Storage 즉시 삭제).
- 이유: D-021의 "새 공간 키"를 key_id 증가 없이 실현하는 가장 단순한 방법이다.

### D-024 · 상대 사진은 Wi-Fi에서 미리 받는다 · 기본값
- 결정: Wi-Fi 연결 중 앱이 앞에 있으면 상대 사진 보관본을 차례로 내려받아 복호화해 둔다. 내보내기·백업·포토북은 시작 전에 빠진 보관본을 먼저 받고, 오프라인이면 "상대 사진 N장을 받아야 해요"로 막는다.
- 이유: 상대 보관본을 열 때만 받으면 오프라인 조회가 안 되고, Drive 백업(D-021의 복구 수단)에 상대 사진이 빠진다.
- 내보내기·백업에서 상대 사진은 보관본(2048px)이다. 원본은 각자 갤러리에만 있다. 설정 > 저장 공간에서 캐시를 지울 수 있다.

### D-025 · 연결 해제 이후 처리 · 기본값 (D-016 보완)
- 해제하면 공간은 `unlinked`가 된다. 30일 동안 두 사람 모두 서버 데이터를 읽기만 할 수 있다(빠진 상대 사진 받기·내보내기용). 쓰기는 막힌다.
- 기기에서는 그 공간을 읽기 전용 "지난 기록"으로 보여준다. 홈에는 [복구 요청] [내보내기] [새로 시작]만 있다.
- 복구: 한쪽이 [복구 요청] → 상대가 앱을 열면 확인 → 둘 다 동의하면 `active`로 되돌린다(`relink_requests`, 30일 안에만).
- 새로 시작: 지난 기록을 기기에서 지우고 새 1인 공간을 만든다. 지우기 전에 내보내기를 권한다. MVP는 기기당 공간 1개만 다룬다.
- 연결 때 "내 기록도 합칠까요?"에 아니오: 내보내기를 권한 뒤 1인 공간을 지우고 합류한다.

### D-026 · 계정 삭제는 연결 해제 + 계정 삭제 · 기본값
- 결정: 커플 공간이면 먼저 연결 해제(D-025)를 하고, 계정·기기·key_grants·member_profiles는 바로 삭제한다. 공간 데이터는 상대가 사진을 받을 수 있도록 30일 뒤 삭제하고, 복구는 할 수 없다.
- 1인 공간이면 서버 데이터를 바로 삭제한다. 기기 데이터도 지운다.
- Apple 로그인 사용자는 Apple REST API로 토큰을 폐기한다(App Store 심사 요건).

### D-027 · 승인 요청만 원격 푸시 · 확정 (2026-10-03)
- 결정: "연결 요청"과 "새 기기 승인 요청" 두 종류만 Expo 푸시로 보낸다. 상대 활동 푸시(D-018)는 계속 제외한다. 문구는 알림 숨김 설정을 따른다.
- 비용: `devices.push_token` 컬럼, 푸시 발송 함수, 푸시 권한 요청 1회.
- 버린 대안: 푸시 없이 요청 화면에 "상대에게 앱을 열어 달라고 말해 주세요"와 메시지 공유 버튼을 둔다.
